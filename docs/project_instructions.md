# ナレッジファイル作成・更新ルール

## 基本方針

このプロジェクトのナレッジは「日付ごとに独立した markdown ファイル」として蓄積する。
既存ファイルを書き換えるのではなく、**今回の作業分を新しいファイルとして生成し、ユーザーがダウンロードしてプロジェクトナレッジにアップロードする**運用とする。

## トリガーフレーズ

ユーザーが「今回の作業をまとめて」「まとめて」「ログ更新」など、
記録を指示する短いフレーズを言ったら、以下を自動で行う:

1. 今回の会話を最初から読み返す
2. 会話の主題を判断して、ファイル名を決める
3. 後述のフォーマットで markdown ファイルを生成する
4. ダウンロード可能な形でユーザーに提示する

ユーザーから内容の指定はない前提。会話ログから自分で抽出する。

## ファイル生成のルール

### 1. ファイル名規則

以下のパターンで命名する:

```
YYYYMMDD_HHMM_テーマ.md
```

- 日時は会話時点の日本時間(JST)
- テーマはスネークケースの英語または日本語
  - 良い例: `20260521_1430_piper_ros_build.md`
  - 良い例: `20260521_1430_moveit2_integration.md`
  - 悪い例: `memo.md`, `log.md`

### 2. ファイル内のフォーマット

```markdown
# テーマを表すタイトル

> 日時: YYYY-MM-DD HH:MM (JST)
> 関連既存ファイル: (あれば既存ナレッジファイル名を書く。なければ省略)

## 実施したこと

(本文)

## 結果

(本文)

## つまずいた点

(本文)

## 学んだこと

(本文)

## 次にやること

(本文)
```

該当する情報がない観点(セクション)は省略してよい。無理に埋めない。

### 3. 出力時の振る舞い

- ファイルを生成したら、ダウンロード可能な形で提示する
- 「このファイルをプロジェクトナレッジにアップロードしてください」の一言だけ添える
- ファイル内容をチャット本文にも長々と再掲しない(冒頭の数行プレビューだけでよい)

## 会話から抽出する観点

会話を読み返すとき、以下の観点で情報を拾う:

- **実施したこと**: 実行したコマンド、書いたコード、行った設定
- **結果**: 成功/失敗、出力ログ、確認できたこと
- **つまずいた点**: エラー、その原因、対処方法
- **学んだこと**: 次回以降に効きそうな知見、注意点
- **次にやること**: 会話の中で言及された TODO、未解決項目

## ファイル内の書き方

### コマンドとログ
- 実行コマンドは ` ```bash ` コードブロック
- ログやエラーは ` ``` ` (言語指定なし)コードブロック
- Python コードは ` ```python `

### 文体
- 簡潔な常体(である調) または 箇条書き
- 絵文字は状態表示にのみ使用
  - ✅ 完了
  - ⚠️ 注意・部分的成功
  - 🔲 未着手

### 既存ファイルへの参照
既存ナレッジファイルの内容に言及する場合は、見出し名を引用する形にする:
  例: 「(参照: `piper_ros2_setup_progress.md` の Step 4.5)」
内容を再掲することはしない。

## やってはいけないこと

- 既存ナレッジファイルの内容を再掲・コピーする
- 「全体ロードマップ」のような全体像を毎回書き直す
- 1つの会話の記録を複数ファイルに分割する(原則1会話 = 1ファイル)
- ユーザーの指示なしに既存ファイルを「書き換えたバージョン」として出力する
